## 1\. 先建立正确模型：世界生成不是一个系统，而是一串流水线

新手常见误区：

-   以为“世界生成 = 加矿脉”
    
-   以为“生物群系 = 颜色 + 温度”
    
-   以为“维度 = 传送门 + 世界 key”
    

实际上它是分层流水线：

1.  **维度元信息层**（时间、坐标缩放、高度范围、视觉效果）
    
2.  **区块生成器层**（地形体素填充：空气/石头/流体）
    
3.  **生物群系来源层**（这个位置应该是哪个 biome）
    
4.  **雕刻器层（carvers）**（洞穴/峡谷）
    
5.  **特征放置层（features）**（矿、树、花、湖泊）
    
6.  **刷怪配置层（spawn settings）**
    
7.  **后处理修改层（BiomeModifier/StructureModifier）**
    

源码对应点：

-   维度类型定义：`DimensionType`
    
-   维度实例定义（类型 + 生成器）：`LevelStem`
    
-   生成器抽象：`ChunkGenerator`
    
-   噪声生成器实现：`NoiseBasedChunkGenerator`
    
-   biome 抽象与数据：`Biome`
    
-   feature 数据结构：`ConfiguredFeature`、`PlacedFeature`
    
-   NeoForge 修改入口：`BiomeModifier`

## 2\. 先读源码再写代码：最关键入口总览（建议收藏）

这张“入口图”是本文方法论核心：

### 2.1 注册表 key 在哪里

看 `Registries`：

-   `worldgen/biome` → `Registries.BIOME`
    
-   `worldgen/configured_feature` → `Registries.CONFIGURED_FEATURE`
    
-   `worldgen/placed_feature` → `Registries.PLACED_FEATURE`
    
-   `dimension_type` → `Registries.DIMENSION_TYPE`
    
-   `dimension`（LevelStem）→ `Registries.LEVEL_STEM`
    
-   `worldgen/noise_settings` → `Registries.NOISE_SETTINGS`
    
-   `worldgen/world_preset` → `Registries.WORLD_PRESET`
    

### 2.2 谁加载这些注册表数据

看 `RegistryDataLoader.WORLDGEN_REGISTRIES` 与 `RegistryDataLoader.DIMENSION_REGISTRIES`。

这解释了为什么 worldgen JSON 路径错误会直接导致注册失败。

### 2.3 NeoForge world 修改入口

-   接口：`BiomeModifier`
    
-   内置实现：`BiomeModifiers`
    
-   serializer 注册：`NeoForgeMod.ADD_FEATURES_BIOME_MODIFIER_TYPE` 等
    
-   动态注册表声明：`NeoForgeRegistries.Keys.BIOME_MODIFIERS`
    
-   启动应用：`ServerLifecycleHooks.runModifiers()`

## 3\. 底层原理一：注册表 + Codec + 数据加载，是世界生成的一切前提

## 3.1 先问“对象是谁”，再问“文件怎么写”

很多教程上来就贴 JSON，但你真正需要先回答三问：

1.  这个对象归哪个 registry？
    
2.  这个对象的 codec 定义在哪？
    
3.  这个 registry 是在哪个阶段被加载？
    

只要三问答清，JSON 自然就会写。

## 3.2 Codec 的本质

以 `DimensionType.DIRECT_CODEC` 为例：

-   `min_y` 有范围约束
    
-   `height` 有范围约束
    
-   构造器还会二次校验（必须 16 的倍数、`min_y + height` 不能越界）
    

所以不是“字段名对了就行”，而是**值域也必须合法**。

再看 `NoiseSettings.CODEC`，有 `comapFlatMap` 额外校验：

-   `height % 16 == 0`
    
-   `min_y % 16 == 0`
    

这就是你经常看到“height has to be a multiple of 16”错误的根因。

## 3.3 数据加载流程如何影响调试

在 `RegistryDataLoader.load` 中，注册表会：

1.  读取 JSON
    
2.  用 codec 解码
    
3.  freeze registry
    
4.  任何错误都汇总后抛异常
    

意味着：

-   一个坏 JSON 可能阻断整个 registry
    
-   日志会打印 registry + element 级错误
    

你排错时必须优先看“最早出现的 decode 错误”。

## 4\. 底层原理二：区块状态机（ChunkStatus）决定生成顺序

世界生成不是“一次函数调用”，而是状态推进。

状态定义在 `ChunkStatus`：

-   `BIOMES`
    
-   `NOISE`
    
-   `SURFACE`
    
-   `CARVERS`
    
-   `FEATURES`
    
-   `LIGHT`
    
-   `SPAWN`
    
-   `FULL`
    

顺序意义：

-   你在错误阶段期待效果，会误判“功能没生效”
    
-   举例：feature 问题不该去怀疑 noise；noise 问题不该先看 spawns
    

辅助理解：`ProtoChunk.getNoiseBiome` 会在 BIOMES 之前直接抛错，说明阶段边界非常严格。

* * *

## 5\. 底层原理三：BiomeModifier 如何“改原版世界”

## 5.1 修改不是替换，而是“拷贝 + 分阶段变更”

关键数据结构：`ModifiableBiomeInfo`

流程：

1.  biome 构造时缓存原始数据（见 `Biome``构造器`）
    
2.  服务端初始化时按阶段应用 modifier（见 `applyBiomeModifiers`）
    
3.  运行期访问会读取修改后数据（例如 `Biome.getGenerationSettings()`）
    

## 5.2 阶段顺序不是装饰，而是逻辑保障

阶段定义：`BiomeModifier.Phase`

典型顺序：

-   `ADD` 先加
    
-   `REMOVE` 再删
    
-   `MODIFY` 最后改值
    

如果你自己写 modifier，不遵循阶段语义，最常见后果是“被后续 modifier 覆盖”。

## 5.3 内置 modifier 能做什么

看 `BiomeModifiers`：

-   加/删 placed features
    
-   加/删 spawns
    
-   加/删 carvers
    
-   加/删 spawn costs
    

它们本质就是对 builder 的列表操作（如 `BiomeGenerationSettingsBuilder.getFeatures()`）。

## 6\. 底层原理四：Feature 放置链（Feature -> Configured -> Placed）

你可以把它理解成：

1.  **Feature**：算法模板（怎么生成）
    
2.  **ConfiguredFeature**：算法 + 参数（生成什么）
    
3.  **PlacedFeature**：配置结果 + 放置规则（在哪儿、几次、以什么分布）
    

对应源码：

-   模板：`Feature`
    
-   配置实例：`ConfiguredFeature`
    
-   放置实例：`PlacedFeature`
    

放置修饰器链路在 `PlacementModifier` 与 `PlacedFeature.placeWithContext`：

-   起点 `BlockPos`
    
-   逐个 modifier 变换成位置流
    
-   对每个位置执行 configured feature 的 `place`
    

### 6.1 Feature 周期冲突（cycle）为什么会报错

特征排序由 `FeatureSorter.buildFeaturesPerStep` 构建图并 DFS 检测。

如果你把同一批 biome 的特征关系弄成循环，最终会抛 `Feature order cycle found`。

这就是“随便塞原版 feature 到新 step”经常炸的底层原因。

## 7\. 底层原理五：噪声地形与生物群系分配（NoiseRouter + Climate）

## 7.1 地形不是“一个噪声”，而是噪声网络

`NoiseGeneratorSettings` 持有 `NoiseRouter`，而 router 本身由 `NoiseRouterData.bootstrap` 建出来。

核心字段包含：

-   continentalness
    
-   erosion
    
-   ridges
    
-   depth
    
-   finalDensity
    

### 7.2 RandomState 负责把“参数化图”实例化成“带 seed 的函数”

看 `RandomState`：

-   根据 seed 创建 noise 实例
    
-   包装路由函数
    
-   构建 `Climate.Sampler`
    

### 7.3 biome 分配通过 Climate 参数空间最近匹配

看 `Climate.ParameterList.findValue` 与 `MultiNoiseBiomeSource.getNoiseBiome`。

直觉上就是：

-   sampler 在某位置采样到 `temperature/humidity/continentalness/...`
    
-   在 parameter list 里找“最匹配”的 biome
    

### 7.4 为什么原版 overworld biome 分布那么复杂

因为它不是硬编码 if-else，而是 `OverworldBiomeBuilder` 通过大量 Climate 参数切片构建。

这也解释了方法论：

-   你要“轻改原版分布”时尽量别重写整个 Overworld 规则
    
-   更推荐在维度里用自定义 `multi_noise.biomes` 从小规模参数空间开始

## 8\. 底层原理六：维度系统（DimensionType + LevelStem + WorldPreset）

## 8.1 DimensionType：描述“这个宇宙的物理规则”

字段定义见 `DimensionType`：

-   时间是否固定
    
-   是否有天空/顶盖
    
-   是否高温
    
-   坐标缩放（影响跨维度换算）
    
-   min\_y / height / logical\_height
    
-   effects（客户端视觉）
    

## 8.2 LevelStem：维度实例的关键组合

`LevelStem`：

-   `type`: DimensionType holder
    
-   `generator`: ChunkGenerator
    

所以“新维度”最小定义一定是这两个。

## 8.3 WorldPreset：创建世界时的维度集合

`WorldPresets` 体现了标准组合：

-   overworld
    
-   nether
    
-   end
    

你要把自定义维度纳入“世界预设”，就得提供 `worldgen/world_preset`。

## 9\. 方法论：四层递进开发法（L1→L4）

这是本文最重要的“工程实践准则”：

### L1：只改原版（BiomeModifier）

-   风险最小
    
-   更新兼容性最好
    
-   适合 80% 内容模组
    

### L2：加自定义特征

-   自己做 configured/placed feature
    
-   用 modifier 注入目标 biome
    

### L3：加自定义 biome

-   有自己的 biome JSON
    
-   加自己的 feature/spawn/carver
    
-   接入 biome source
    

### L4：加自定义维度

-   新 dimension\_type
    
-   新 level\_stem
    
-   新 world\_preset
    
-   独立 biome 分布策略
    

每层只新增一个复杂度，保证可验证、可回滚。

## 10\. 实战 L1：修改原版世界生成（最低风险，最高性价比）

本章给一整套可直接复制改造的模板。

## 10.1 目录结构（务必正确）

```
data/
  <modid>/
    neoforge/
      biome_modifier/
        add_ore_to_overworld.json
        remove_vanilla_ore_from_plains.json
        add_custom_spawns.json
        remove_zombie_from_swamp.json
        add_carver_example.json
        remove_carver_example.json
```

> 注意：`biome_modifier` 在 `neoforge/` 下，不在 `worldgen/` 下。

## 10.2 示例 1：给所有主世界 biome 加矿

`data/<modid>/neoforge/biome_modifier/add_mythril_ore_to_overworld.json`

```json
{
  "type": "neoforge:add_features",
  "biomes": "#minecraft:is_overworld",
  "features": "<modid>:ore_mythril_placed",
  "step": "underground_ores"
}
```

## 10.3 示例 2：只从指定 biome 删除某个矿

`data/<modid>/neoforge/biome_modifier/remove_diamond_from_plains_forest.json`

```json
{
  "type": "neoforge:remove_features",
  "biomes": ["minecraft:plains", "minecraft:forest"],
  "features": "minecraft:ore_diamond",
  "steps": "underground_ores"
}
```

## 10.4 示例 3：新增刷怪

`data/<modid>/neoforge/biome_modifier/add_spawn_zombie_overworld.json`

```json
{
  "type": "neoforge:add_spawns",
  "biomes": "#minecraft:is_overworld",
  "spawners": {
    "type": "minecraft:zombie",
    "weight": 25,
```

## 14\. 进阶：自定义 BiomeModifier 类型（Java 侧扩展）

当内置 `neoforge:add_* / remove_*` 不够时，用 Java 扩展。

## 14.1 接口实现骨架

```java
package com.example.examplemod.worldgen;

import com.mojang.serialization.MapCodec;
import net.minecraft.core.Holder;
import net.minecraft.world.level.biome.Biome;
import net.neoforged.neoforge.common.world.BiomeModifier;
import net.neoforged.neoforge.common.world.ModifiableBiomeInfo;

public record ForceRainBiomeModifier(float minDownfall) implements BiomeModifier {
    @Override
    public void modify(Holder<Biome> biome, Phase phase, ModifiableBiomeInfo.BiomeInfo.Builder builder) {
        if (phase != Phase.MODIFY) return;
        var climate = builder.getClimateSettings();
        if (climate.getDownfall() < minDownfall) {
            climate.setDownfall(minDownfall);
        }
    }

    @Override
    public MapCodec<? extends BiomeModifier> codec() {
        return ModBiomeModifierCodecs.FORCE_RAIN.get();
    }
}
```

## 14.2 serializer 注册

```java
package com.example.examplemod.worldgen;

import com.mojang.serialization.MapCodec;
import com.mojang.serialization.codecs.RecordCodecBuilder;
import net.neoforged.neoforge.common.world.BiomeModifier;
import net.neoforged.neoforge.registries.DeferredHolder;
import net.neoforged.neoforge.registries.DeferredRegister;
import net.neoforged.neoforge.registries.NeoForgeRegistries;

public final class ModBiomeModifierCodecs {
    public static final DeferredRegister<MapCodec<? extends BiomeModifier>> REG =
        DeferredRegister.create(NeoForgeRegistries.Keys.BIOME_MODIFIER_SERIALIZERS, "examplemod");

    public static final DeferredHolder<MapCodec<? extends BiomeModifier>, MapCodec<ForceRainBiomeModifier>> FORCE_RAIN =
        REG.register("force_rain", () -> RecordCodecBuilder.mapCodec(i -> i.group(
            com.mojang.serialization.Codec.FLOAT.fieldOf("min_downfall")
                .forGetter(ForceRainBiomeModifier::minDownfall)
        ).apply(i, ForceRainBiomeModifier::new)));
}
```

## 15\. 进阶：地表规则（SurfaceRules）与噪声参数定制思路

地表（顶层方块）受 `surface_rule` 控制，定义在 `noise_settings` 里。

源码入口：`SurfaceRules`。

## 15.1 你要知道的核心事实

-   SurfaceRules 也是 codec 分发体系
    
-   condition 与 rule 都可组合
    
-   实际计算发生在噪声生成阶段
    

## 15.2 定制策略建议

新手不要从 0 写完整 surface rule，建议：

1.  先复用原版 `minecraft:overworld` noise settings
    
2.  只在 biome 层做特征与方块表现
    
3.  等系统稳定后再 fork noise settings 做 surface rule 小改
    

## 15.3 何时必须自定义 noise settings

-   你要非标准高度（例如低重力浮空大陆）
    
-   你要彻底改地形风格（非 Overworld 逻辑）
    
-   你需要独立 spawn target 气候参数
    

相关定义：`NoiseGeneratorSettings`。

## 17\. 排错大全：从日志到根因定位（按错误类型索引）

以下按“报错现象 -> 根因 -> 解决方式”组织。

### 17.1 `Unknown registry element` / `Failed to parse`

常见根因：

-   路径放错注册表目录
    
-   `type` 写错命名空间
    
-   引用了不存在的 feature/carver/biome
    

定位方法：

1.  看报错里 registry 名
    
2.  对照 `Registries`
    
3.  回查资源路径与 id
    

### 17.2 `height has to be multiple of 16`

根因：`dimension_type` 或 `noise_settings` 里高度参数不合法。

依据：`DimensionType``构造校验`、`NoiseSettings.guardY`。

### 17.3 `Feature order cycle found`

根因：feature step 关系形成循环。

依据：`FeatureSorter.buildFeaturesPerStep`。

处理：

-   不要随意跨 step 搬运 vanilla 特征
    
-   先从单个 injected feature 开始
    

### 17.4 “新 biome 不生成”

根因：未接入 biome source 参数空间。

定位：检查 `dimension` 文件里的 `biome_source` 配置。

### 17.5 “modifier 写了但看不到效果”

根因候选：

-   modifier 文件路径错误
    
-   `biomes` 过滤条件没命中
    
-   `features` 引用 ID 不存在
    
-   被后续 modifier 覆盖
    

验证点：`ServerLifecycleHooks.runModifiers` 生命周期时序。

### 17.6 “维度存在但创建世界界面选不到”

根因：缺少 `world_preset` 或 preset 未被使用。

对照：`WorldPresets.bootstrap` 的标准模式。

### 17.7 “能进维度但地形异常/全空/全石”

根因候选：

-   `generator.settings` 与 `dimension_type` 高度不匹配
    
-   自定义 noise settings 参数不合法
    
-   surface rule 不适配
    

先回退到 `minecraft:overworld` settings 做基线，再逐步改。

### 17.8 “刷怪异常（过多/过少/无刷怪）”

检查：

-   biome 的 `spawn_settings`
    
-   biome modifier 是否 add/remove 了 spawns
    
-   spawn costs 是否过严
    

参考：`MobSpawnSettings`。

## 18\. 性能与稳定性：世界生成不是越复杂越好

## 18.1 复杂度来源

-   biome 参数点数量过多
    
-   feature 放置次数高 + 条件复杂
    
-   过多 carvers
    
-   过度自定义噪声网络
    

## 18.2 经验阈值建议

-   新维度初期 biome 数量：2~5
    
-   每 biome 新增 placed feature：先 1~3
    
-   每次迭代只改一个方向（分布/频率/高度）
    

## 18.3 为什么要“渐进式调参”

因为世界生成故障往往是组合问题。 一次改 10 个参数，你几乎无法定位根因。

## 20\. 总结：你应该真正带走的能力

学完这篇之后，你不该只会“照抄一个 json”。 你应该获得的是下面这 6 个能力：

1.  **能分层定位问题**：维度、地形、biome、feature、spawn、modifier 分得清
    
2.  **能从源码反推数据格式**：先看 registry，再看 codec，再写文件
    
3.  **能做低风险迭代**：L1→L4 逐层推进，不一口吃成胖子
    
4.  **能解释每个参数为什么存在**：不是玄学调参
    
5.  **能写可维护 worldgen 资源**：目录、命名、依赖、验证流程成体系
    
6.  **能在版本升级时有章可循**：先看 codec 与 registry 变化，再迁移数据
    

如果你按本文方法执行，世界生成开发会从“黑盒碰运气”，变成“可设计、可验证、可迭代”的工程工作流。
